# AutoQuant 执行控制与紧急停机设计

- 日期：2026-07-22
- 状态：持久化 kill switch、证据化复位与单次对账监督器已实施
- 安全边界：真实交易配置在本版本无条件拒绝

## 1. 默认失败关闭

每个 `AQ_PAPER_ACCOUNT_ID` 首次启动时创建独立控制状态，初始即为 `active`。状态包含
单调版本、稳定原因、操作者、UTC 时间和最后事件哈希。服务启动依次验证执行账本重放
和控制事件重放；任一步失败都不得启动交易能力。执行账本恢复失败还会先尝试记录
`recovery_failed` 激活命令。

## 2. 激活来源

控制原因区分人工停机、对账失败、依赖不可用、订单状态未知、恢复失败和演练。对账
监督器读取内部与券商快照、持久化对账报告，并在差异或依赖异常时自动激活。通过的
对账不会自动复位，避免短暂恢复静默解除人工或系统停机。

控制台只提供经过 Basic Auth 与 CSRF 校验的激活接口。重复相同命令幂等；相同命令号
绑定不同内容会拒绝。接口不返回底层异常或凭据。

## 3. 复位证据

复位不开放为 Web 操作。存储层同时要求：

- 操作者提供当前控制版本，防止并发状态被覆盖；
- 引用同一账户、近期、`reconciled=true` 的持久化对账报告；
- 调用方已经完成执行历史恢复验证；
- 命令时间不早于证据，证据未超过规定时效。

任一条件缺失、证据过期或数据库不可用都保持 active。

## 4. 不可变审计

schema v9 将每个初始化、激活和复位命令写入前序哈希事件链。事件禁止更新和删除；
控制投影只允许版本加一、时间前进且账户身份不变。读取时重新计算命令、事件和状态
哈希，并通过完整事件重放验证当前投影。

## 5. 当前剩余门槛

单次对账监督器尚未配置真实模拟券商与内部账户快照适配器，因此还没有持续调度。
完整演练还需要证明订单流在激活后被拒绝、进程重启后保持停机、故障恢复后只能用
新鲜证据人工复位。QMT 隔离网关和任何真实订单继续禁止。
