# AutoQuant Tushare 日频可信数据接入设计

**日期：** 2026-07-22  
**状态：** 用户已批准方案方向，等待书面规格复核

## 1. 目标

在不购买 Tushare 历史分钟权限的前提下，为 AutoQuant 增加一条独立、可审计、
默认安全关闭的 A 股日频数据管道。第一阶段以用户已达到的 2000 积分权限为边界，
采集未复权日线、复权因子、交易日历、证券生命周期和停复牌证据，为后续日频回测
提供 point-in-time 数据基础。

本阶段只解决数据可信度和可复现性，不实现策略、回测收益、选股、模拟交易或实盘
下单，也不承诺数据权限能够产生利润。

## 2. 已确认约束

| 项目 | 决定 |
|---|---|
| 数据源 | Tushare Pro HTTP API |
| 当前权限 | 2000 积分；未购买独立历史分钟权限 |
| 第一阶段频率 | 日频 |
| 第一阶段市场 | 沪深主板、创业板、科创板；保持原系统市场边界 |
| 原始价格 | `daily` 未复权价格 |
| 复权 | `adj_factor` 独立存储，查询或研究阶段计算 |
| 完整性证据 | `trade_cal`、`stock_basic`、`suspend_d`（以真实账号探测结果为准） |
| 失败策略 | 权限、覆盖证据、质量检查或审计存储不足时 fail closed |
| 凭证 | 仅从 `AQ_TUSHARE_TOKEN` 读取，不进入 Git、日志、异常或测试快照 |
| 原 RQData 管道 | 保留，不删除、不伪装成 Tushare，也不用于当前验收 |

Tushare 的积分接口与历史分钟独立权限是两套授权。系统不得因为积分达到 2000 就
假设 `stk_mins` 可用，也不得在日频命令内调用该接口。

## 3. 方案选择

采用“独立日频垂直切片”，不把日线伪装成某个收盘时刻的分钟线，也不在本阶段将
所有行情模型重构成任意频率的通用框架。

原因如下：

1. 日线与分钟线的时间语义、完整性检查和可用时间不同，复用同一记录会制造错误语义。
2. 独立模型能保留现有分钟管道的验证成果，并为未来增加 Tushare 分钟适配器留下接口。
3. 当前最重要的是形成一条可以真实运行的小型闭环，而不是提前承担全系统抽象重构风险。

## 4. 组件与职责

```text
Tushare Pro HTTPS
        │
        ▼
TushareHttpClient
  ├── daily
  ├── adj_factor
  ├── trade_cal
  ├── stock_basic
  └── suspend_d
        │
        ▼
TushareDailySource
  ├── 代码映射与单位换算
  ├── 可用时间策略
  └── 原始响应证据/内容哈希
        │
        ▼
DailyIngestionService
  ├── DailyBarQualityGate
  ├── 覆盖证据检查
  ├── ClickHouse 追加式记录
  └── PostgreSQL 清单/检查点/审计链
```

### 4.1 HTTP 客户端

直接使用现有 HTTPX 技术栈调用 Tushare 标准 POST 协议，不增加 Tushare Python SDK。
请求体只在发送边界组装 `api_name`、`token`、`params` 和 `fields`；任何诊断信息必须
先删除或遮盖 `token`。

客户端职责：

- 强制使用可配置的 HTTPS 基础地址；
- 解析 Tushare 的业务状态码、消息、字段列表和行列表；
- 将权限拒绝与网络故障、限流、服务端故障、响应契约错误区分为稳定异常类型；
- 只对明确的瞬时故障进行有上限的指数退避重试；
- 对日期区间进行有界分片，不能把“单次请求未返回全部数据”误判为完整；
- 保存不含凭证的原始响应字节或规范化响应作为 `SourceEvidence`，并计算 SHA-256；
- 在异常和结构化日志中只出现接口名、参数摘要、请求标识与脱敏消息。

### 4.2 数据源适配器

`TushareDailySource` 实现新的日频源协议，不实现现有 `MarketDataSource` 分钟协议。
供应商代码映射为 AutoQuant 现有规范：例如 `000001.SZ` 映射为 `000001.XSHE`，
`600000.SH` 映射为 `600000.XSHG`。不支持或含糊的交易所后缀直接拒绝。

Tushare `daily` 的成交量和成交额在源接口中的单位分别按“手”和“千元”解释；内部
规范化为“股”和“元”。换算采用 `Decimal`，禁止二进制浮点参与内容哈希或持久化。

## 5. 日频领域模型

### 5.1 `DailyBarRevision`

每条记录至少包含：

- `source`、规范化证券代码、交易日；
- 未复权 `open`、`high`、`low`、`close`、`pre_close`；
- 成交量（股）、成交额（元）；
- `available_at`、`ingested_at` 和版本化可用时间策略；
- 供应商修订标识、源证据哈希和确定性内容哈希。

原始记录追加写入。Tushare 后续修订同一证券同一交易日的数据时，生成新 revision，
不覆盖历史 revision。研究查询必须提供 `as_of`，并且只能选择
`available_at <= as_of` 的最新可见 revision。

### 5.2 `AdjustmentFactorRevision`

复权因子以独立 revision 保存，键为证券代码和交易日。它不能提前乘入原始 OHLC，
也不能让未来除权事件改变过去某次研究运行所看到的数据。复权序列由查询层根据
明确的 `as_of` 和基准日计算。

### 5.3 覆盖证据

交易日历、证券上市/退市状态和停复牌事件作为独立来源证据保存。质量门根据目标证券
在请求日期范围内的生命周期构造预期交易日，然后将无日线记录的日期分类为：

- 非交易日；
- 尚未上市或已经退市；
- 已知停牌；
- 无法解释的缺失。

只有前三类可以解释缺失。任何无法解释的缺失、相互冲突的状态或所需接口无权限，
都禁止生成 `completed` 数据集清单。

`suspend_d` 等接口的具体权限以 `tushare-check` 对当前账号的只读探测为准。2000 积分
不是代码中的硬编码授权证明；接口返回权限拒绝时，程序报告缺失能力，不做推测性降级。

## 6. 时间与防前视策略

所有持久化时间统一为 UTC，交易日语义使用 `Asia/Shanghai`。

第一版采用保守的 `tushare-daily-v1` 可用时间策略：某交易日的日线和复权因子在研究
视角中最早从下一交易日开盘开始可用。即便供应商通常在收盘后更早更新，也不允许
同一交易日的完整收盘数据驱动当日成交。未来若引入真实发布时间证据，必须新增策略
版本，不能改写旧记录的可用时间含义。

## 7. 质量门和持久化

日线质量门至少检查：

- 价格和成交单位的类型、精度及非负约束；
- `low <= open/close <= high`；
- 同一批次中的重复或相互冲突 revision；
- 返回证券和日期是否超出请求范围；
- 交易日历、生命周期、停牌和价格记录是否一致；
- 请求范围是否被所有响应分片完整覆盖；
- 源证据哈希、内容哈希和 revision 标识是否存在且确定；
- 零成交量记录不被自动当作缺失，缺失也不被自动填成零成交量。

新增 ClickHouse 日线 revision 表和复权因子 revision 表，通过新的增量迁移创建；不修改
已经合并的 phase-1 基线迁移。PostgreSQL 继续保存检查点、质量报告、数据集清单和
哈希链审计事件；如现有结构不能表达日频数据集，则通过新迁移扩展，而不是重写历史
迁移。

一次采集只有在以下顺序全部成功后才能推进检查点：下载并验证源证据、通过质量门、
追加 ClickHouse revision、保存质量报告、写入不可变清单、追加审计事件。中途失败不得
产生成功清单，也不得越过失败区间推进检查点。

## 8. 配置和 CLI

配置新增：

- `AQ_TUSHARE_TOKEN`：必需的 `SecretStr`；
- `AQ_TUSHARE_API_URL`：默认官方 HTTPS API 地址；
- 可选的超时、重试和保守限速设置，必须有安全上限。

CLI 新增：

- `autoquant tushare-check`：验证配置，并对第一阶段接口做最小只读能力探测；输出
  `available`、`permission_denied` 或 `error`，从不输出 Token；
- `autoquant ingest-daily`：接受证券、起止交易日和明确的生产完整性开关，执行日频
  垂直切片；
- `autoquant config-check`：增加 Tushare 配置状态，同时保留 RQData 状态。

配置检查不把“Token 格式存在”当作权限成功。生产完整性请求中任一必需能力不可用时，
命令以非零状态退出，并留下可审计的失败信息。

## 9. 测试与验证策略

实现采用测试驱动开发：

1. 配置测试证明 Token 必需、使用秘密类型且不会被序列化泄漏；
2. HTTP 契约测试覆盖请求形状、字段顺序无关解析、业务错误、权限拒绝、限流和重试；
3. 映射测试覆盖交易所代码、Decimal 单位换算、响应倒序和空结果；
4. 模型与性质测试覆盖确定性哈希、追加 revision 和时间约束；
5. 质量测试覆盖停牌、未上市、非交易日、异常缺失和冲突证据；
6. 持久化测试覆盖幂等追加、point-in-time 查询和检查点不越界；
7. CLI 测试覆盖脱敏、退出码和权限矩阵；
8. 默认测试全部使用模拟响应，不消耗 Tushare 配额；
9. opt-in live smoke test 只读取一个已知证券的极小日期范围，并且只有用户在远端自行
   配置新 Token 后才运行。

项目验收同时运行非 live pytest、Ruff、mypy，并在授权数据库存在时运行 PostgreSQL、
ClickHouse 集成测试。因数据库或 Token 缺失而跳过的测试只记录为未验证证据，不能被
宣称为真实端到端成功。

## 10. 安全与运维

聊天中曾出现的旧 Token 视为已经暴露，不得用于开发、测试或验证。用户需要在 Tushare
后台轮换 Token，并只在 `rlocal` 的未跟踪环境文件或进程环境中设置新值。

限速必须低于账号理论上限并带抖动，避免并发任务共同耗尽额度。程序记录每个接口的
调用计数和批次范围，但不记录凭证或完整请求体。购买更高积分、分钟权限或实时行情
不属于本阶段实施动作，必须由后续策略证据单独驱动。

## 11. 验收标准

第一阶段完成需要同时满足：

1. 无 Token、无权限或错误 Token 均 fail closed 且不泄漏秘密；
2. 对一个指定沪深证券和日期范围，能采集日线、复权因子及完整性证据；
3. 能正确区分非交易日、生命周期外、停牌和异常缺失；
4. 重复运行不覆盖旧 revision，也不制造不一致的成功清单；
5. point-in-time 查询不能看到 `as_of` 之后才可用的日线或复权因子；
6. 所有默认自动化检查通过；
7. 用户在远端配置轮换后的 Token 后，`tushare-check` 给出真实权限矩阵；
8. 只有真实 Tushare、PostgreSQL 和 ClickHouse 纵向流程成功后，才可宣布生产数据管道
   可运行。

满足这些条件只证明数据基础达到约定的可信度，不证明任何策略能够盈利。
