# AutoQuant 模拟订单协调器设计

- 日期：2026-07-23
- 状态：内部协调器与数据库集成验证已实施；无 Web 下单入口、无 QMT 连接
- 安全边界：只允许 `paper` 风控决策与本地零网络模拟券商，真实交易继续硬锁

## 1. 单一账户周期

每次调用按固定顺序执行双源对账、停机状态读取、盘前风控、不可变决策写入、本地订单
创建、模拟券商提交、回报消费和提交后再对账。风控拒绝仍写入审计账本，但不会创建
订单或券商事实。任一对账差异会激活持久化 kill switch。

PostgreSQL 会话级 advisory lock 覆盖整个周期。等待者使用 `pg_try_advisory_lock` 轮询，
不会占满连接池后互相等待。不同进程对同一账户的订单因此不能同时读取同一份旧资金
快照；数据库并发测试证明，两笔各占约 60% 资金的订单并发进入时只有第一笔成交，第二
笔基于更新后的现金被风控拒绝。

## 2. 提交围栏

协调器在风控通过和本地订单落库后再次读取 kill switch，并把控制状态哈希作为提交
围栏传给模拟券商。券商事务对控制行执行 `FOR SHARE`，要求账户、非激活状态及哈希
全部一致，随后才创建券商事实。并发的停机更新要么先完成并令提交失败，要么等待已经
进入事务的提交完成，不存在读取旧状态后无约束发单的窗口。

## 3. 崩溃恢复与幂等性

若券商事实已经存在，重试只重放并消费这些事实；相同回报不会重复产生内部事件。若
只存在本地批准单，协调器只有在原风险决策哈希、策略哈希、行情哈希均一致，停机状态
未变化，且原行情和决策仍在时效窗口内时才允许幂等续发。超过窗口会保留批准单、记录
差异并激活 `order_state_unknown`，不会用新价格盲目重发。

## 4. 尚未开放的原因

协调器请求中的日初权益、峰值权益和当日累计换手仍需要独立、持久化且可重放的会话
风险状态来源；行情也只是单次调用证据，尚无连续时效监督和交易时段调度。下一阶段先
补齐这些来源与故障注入，再考虑只读模拟盘状态和受控纸面订单入口。真实交易和 QMT
提交在所有证据门槛通过前保持硬锁。
